## 0. 왜 이 문서가 있나

사용자는 Orca(v1.4.207)를 매일 쓴다. 원격 접속과 모바일이 편해서 만족한다. 다만 아래 두 가지가 불편하다(사용자 원문 요지, 2026-10-07~08).

1. **세션을 여러 개 켜 두고 일하다 보니, 각 세션이 지금 무슨 일을 하는지 찾기 힘들다.**
2. **세션이 길어지면 그 세션이 원래 무슨 일을 하던 세션인지 알기 힘들다.**

사용자는 **에이전트가 일을 못 해서 생긴 문제는 없다**고 확인했다. 지금 겪는 고통은 실행 품질이 아니다. **세션의 정체성과 현재 상태를 파악하기 어렵다는 것**이다.

사용자가 명시한 요구:

- 관리 에이전트 하나로 여러 세션을 관리·지시한다는 원래 비전을 유지한다.
- Orca 의 개념을 흡수해 포함하고, 그 위의 상위 레이어까지 갖춘다.
- **사용성이 좋아야 한다.**
- **시킨 일을 잘 해야 한다.**
- **Orca 처럼 여러 머신을 붙여서 관리할 수 있어야 한다.**


### 0.1 2026-10-11 개정 — 채팅 중심

사용자 원문: "내가 원한건 단순하게 세션 스냅샷 모여있는 화면이 필요한게 아니잖아. 채팅을 통해서 모든 세션을 아우를 수 있는걸 원한건데."

- **화면 중심**: 보드가 아니라 채팅이다. C1 의 채팅 상대는 조회 도구만 가진 전용 에이전트 **세션 비서**다(기존 Top 에 붙이면 Top 의 셸·쓰기·위임 권한과 비신뢰 텍스트가 섞여 경계가 서지 않음 — C1 brief §0). 보드는 채팅 답의 근거를 여는 보조 패널로 흡수한다.
- **새 순서** (codex 교차검토 합의 + 사용자 선택):
  1. **C1** 채팅 조회 — I3 의 "관리 에이전트 조회"를 I0a 스냅샷 위로 앞당긴다. 최소 C3(보드 디자인 정리·매니저 화면 흡수)를 함께 한다. 구현 brief: [c1-session-hub-chat-brief.md](./c1-session-hub-chat-brief.md).
  2. **측정** — §6 의 U1~U3 기준(정확성·표본·시간)을 유지하고, 수행 인터페이스를 채팅으로 바꿔 잰다. I0a 보드 측정은 이것으로 대체한다. **C2 는 C1 수락 통과 뒤에만** 착수한다.
  3. **C2** 기존 Orca 세션에 지시 보내기 — I4 의 "기존 세션 전달"을 검증된 경로 하나에서 연다. Orca `terminal send` 를 쓰므로 위 머리말의 "Orca 연결은 관측 전용" 경계를 이 단계에서 **명시적으로 개정**한다. 조건: 사람의 명시적 요청에서 시작, cookie 승인, 대상·실행 incarnation·본문 고정, 전송 직전 재검증, 승인·전송 durable 기록. 별도 구현 brief 필수.
  4. I0b·I1·I2 는 측정에서 드러난 병목(신선도, coverage, 귀속, 머신 등록 비용)을 근거로 고른다. 미리 예정하지 않는다.
- **에이전트가 읽는 범위** (사용자 결정): 지시 내용(작업 머신에서 살균한 것) + **사용자가 요청했을 때만** 터미널 최근 출력(C1b). `/api/observe` 는 cookie-only 로 두고, 별도 broker 에 활성 세션 비서 실행 전용 읽기 권한을 둔다.
- §7 의 I0~I5 설명은 기록으로 남긴다. 순서와 화면 중심은 이 절이 우선한다.

### 0.2 2026-10-20 개정 — 독립 동작 + 채팅으로 세션 운영

사용자 원문(2026-10-20): "orca 비공개 계약에 묶이면 안되. 오픈소스 도입하더라도, 의존성 없이 독자적으로 할 수 잇는 형태여야해."
컨셉 재검토(외부 조사 + codex R1 "컨셉 개정 필요" → R2 GO-WITH-CHANGES, §11) 뒤 사용자가 고른 결정:

| 결정 | 선택 |
|---|---|
| 독립의 범위 | **Orca 없이 핵심 기능이 동작**한다. 벤더 공식 인터페이스·SSH·tailnet·Palantir 로컬 수집기는 써도 된다 |
| 주 입력 환경 | **채팅 중심**. Palantir 가 세션을 띄우고, 사람은 Palantir 채팅에서 지시·승인한다 |
| 수집 hooks | 각 머신의 Claude·Codex 사용자 설정에 **opt-in 설치 허용**(기존 항목 보존, 제거 경로 제공) |
| 외부 세션(Orca 등) | **관측만**. 인계는 원 실행 종료가 확인될 때만, 확인 불가면 거부 |

**정체성** — Palantir 는 여러 머신의 AI 코딩 세션을 직접 띄우고, 하나의 채팅에서 지시·승인·상태·결과를 다루는 독립 관제 허브다. 밖에서 시작한 세션은 벤더 공식 hooks 로 관측하되 지시하지 않는다. Orca 는 선택 연동이다.

이 절은 §0.1 과 아래 본문보다 우선한다. 바뀌는 계약은 다음과 같다.

#### 0.2.1 의존 원칙
1. **핵심 경로(관측·상태·지시·모바일)는 Orca 가 설치돼 있지 않아도 성립한다.** Orca adapter 는 기본 꺼짐, 켜면 보강 정보만 더한다. Orca 값이 핵심 상태를 덮어쓰지 않는다.
2. **외부 계약은 벤더가 문서로 공개한 인터페이스를 우선한다**: Claude Code·Codex hooks, Claude stream-json / Agent SDK, `codex exec --json` / `exec resume`, CLI 의 resume 플래그.
3. **문서에 안정 계약이 아니라고 적힌 형식은 교체 가능한 보조 경로로만 쓴다**: transcript JSONL(Codex 문서가 "isn't a stable interface" 로 명시), `codex app-server`("experimental, not supported for production"). 깨지면 coverage 공백으로 드러나야 하고, 제품이 멈추면 안 된다.
4. **자동 지시에 TUI 키 주입을 쓰지 않는다.** tmux send-keys 는 키를 전달할 뿐, 그 키가 해당 대화에 정확히 한 번 제출됐다는 계약이 없다. tmux 는 사람이 붙어 보는 창이나 프로세스 격리에만 쓴다.
5. **오픈소스는 MIT·Apache 계열 부품이나 설계 패턴만 들인다.** 들인 부품은 vendoring·교체가 가능해야 한다. AGPL 코드(예: claudecodeui)는 반입하지 않는다. ACP(Agent Client Protocol)는 어댑터 경계 설계의 참고로 두고, 도입은 Claude·Codex 어댑터가 안정판이 될 때 다시 본다.

#### 0.2.2 상태 계약 (3축)
단일 `working/waiting/ended` 를 세 축으로 나눈다. **"지시 뒤 종료 기록이 없음"은 `running` 의 증거가 아니다**(현재 `scripts/lib/sessionTranscriptCore.cjs` 의 열린 턴 = working 규칙은 이 계약으로 바뀐다).

| 축 | 값 | 증거 |
|---|---|---|
| 생존 | alive / exited / unreachable / unknown | 소유 세션은 호스트의 프로세스 관측, 외부 세션은 hook 신선도 창(만료 = unknown, dead 아님) |
| 상호작용 | running / awaiting_permission / awaiting_user / idle / unknown | hook·프로토콜 이벤트. 대기는 해제·만료 규칙이 있을 때만 확정 |
| 결과 | 응답 끝남 / 완료 자기보고 / 검증 통과·실패 | 기존 §3.1-7 그대로. 서로 섞지 않는다 |

#### 0.2.3 세션 호스트 (채팅 중심의 본체)
- 사람이 매일 쓰는 세션을 Palantir 가 띄우고 소유한다. 지시는 소유 세션에만, 공식 programmatic 인터페이스로 보낸다.
- **지원 능력은 provider·버전·실행 모드별로 따로 판정하고 화면에 표시한다**: `observe` / `prompt` / `tool_approval` / `cancel` / `resume`. "Claude 지원" 한 칸으로 합치지 않는다.
- **현재 엔진은 사람용 호스트가 아니다**(codex R2, 코드 확인). 새 호스트 경로를 따로 만든다:
  - Claude manager adapter 는 기본 `bypassPermissions`, 실행 중 도구 승인 경로 없음, `cancelTurn()` 미구현(`server/services/managerAdapters/claudeAdapter.js`, `streamJsonEngine.js`).
  - Codex adapter 는 `--dangerously-bypass-approvals-and-sandbox` 강제(`codexAdapter.js`). 실행 중 승인은 `exec` 로 안 되고 app-server(실험적)에만 문서화돼 있다.
  - Claude 정규화 메시지 5,000자 절단 — 원문 보존과 화면 표시 정책을 분리해야 한다.
  - `accepted:true` 는 provider 수신 증거가 아니다. 원격 자식이 아직 붙지 않았으면 메모리 버퍼(`pendingInput`)에 넣고도 true 다(`streamJsonEngine.js` runTurn). 즉 "stdin 에 썼다"조차 보장하지 않는다. 전달 상태는 §0.2.6 으로 다룬다.
- **새 호스트는 Top/Operator/Worker 없이도** 시작·대화·승인·종료·재시작 복구가 돼야 한다. manager 의 권한·프롬프트·토큰 정책을 상속하지 않는다.
- 사람이 같은 세션을 터미널로 잇고 싶으면 CLI 공식 resume 으로 넘긴다. Palantir 쪽 실행을 먼저 멈추고 넘기며, 동시에 두 곳에서 실행하지 않는다.

#### 0.2.4 외부 세션
- Orca 나 수동으로 시작한 세션은 관측 전용이다. Palantir 는 그 세션에 입력을 보내지 않는다. 기존 C2(Orca `terminal send`) 계획은 **폐기**한다.
- 인계(Palantir 소유 실행으로 resume)는 이 순서로만 한다: 원 실행 중지 확인 → 마지막 기록 대조 → 소유권 이전 → 새 실행. 중지를 확인할 수 없으면 인계하지 않는다. resume 은 대화 이력 복구이지 프로세스·도구·환경 전체의 이전이 아니다.

#### 0.2.5 관측 수집 (hooks)
- 1차 소스는 공식 hooks(UserPromptSubmit·Stop·Notification/PermissionRequest·SessionEnd 등)다. hooks 는 CLI 설정이라 Orca 안에서 도는 세션도 Orca 계약 없이 관측된다. 기존 transcript reader(ssh 번들)는 백필·대조 보조다.
- 허브가 꺼져 있으면 http hook 이벤트는 조용히 사라진다. 그래서 **로컬 수집기가 먼저 기록(spool)하고 따로 전송**한다.
- **수집 전용 인증이 선행이다**(§7 I2 그대로): 머신별 수집 capability, 서버가 derive 하는 머신 신원, 개별 폐기·회전. human·PM 토큰은 일반 bearer 로 통과하므로 수집기에 넣지 않는다.
- 설치기는 기존 항목(Orca 훅 포함)을 보존하고, 자기 항목만 제거하고, 중복 설치를 막는다. 설치 후 Orca 훅이 계속 동작하는지 검증한다. Codex 의 비관리 hook 해시 trust 재검토 비용은 설치 버전에서 실측한다. "설치됨"과 "발화함"은 따로 확인한다.

#### 0.2.6 전달 안전 — 공통 계약 (SH1 의 선행 조건)
사람이 소유 세션 채팅에 직접 친 지시든, 비서가 만든 초안을 승인한 것이든, **도구 승인 응답이든** 같은 계약을 따른다. 폐기한 C2 의 보장(§0.1-3)은 대상만 소유 세션으로 바꿔 그대로 유지한다.
1. **고정**: 요청에는 대상 세션·실행 incarnation·본문(도구 승인이면 대상 요청 id 와 응답)이 고정된다. 승인 뒤에는 바꿀 수 없다.
2. **전송 직전 재검증**: 대상 incarnation 이 그대로인지, 아직 그 입력을 받을 상태인지 다시 확인한다. 다르면 보내지 않고 사람에게 돌려준다.
3. **durable 기록**: 요청·승인·전달 상태를 보내기 전에 기록한다. 상태는 `queued → written → provider_observed → completed | unknown` 이다.
4. **멱등**: 새로고침·재접속·폰과 데스크톱 중복 탭이 같은 요청을 두 번 보내지 않는다.
5. **결과 불명이면 자동 재전송하지 않는다.** 조회·대조 결과를 보여 주고, 사람이 다시 보낼지 정한다.

#### 0.2.7 수명과 신뢰 전제
- **서버 재시작이 진행 중인 작업을 죽이지 않는 것을 목표로 한다.** 채팅 중심에서는 소유 세션이 사용자의 일상 작업이기 때문이다. 수단(분리된 호스트 프로세스 등)은 SH1 brief 에서 정한다. 목표를 못 지키는 경우(정상 종료 포함)에는 중단을 명시적으로 기록·표시하고, 조용히 끊기지 않게 한다.
- **재연결과 이력 resume 을 구분한다.** 재연결 = 살아 있는 같은 실행에 다시 붙는다. resume = 새 실행이 대화 이력을 이어받는다. 화면과 기록에서 둘을 다르게 표시한다.
- **이전 실행의 생존이 불명이면 새 실행·resume 을 시작하지 않는다**(같은 대화의 두 실행 방지, §0.2.4 인계 규칙과 같은 원칙).
- **신뢰 전제**: 소유 세션은 사용자 계정 권한으로 사용자 머신에서 돈다. 같은 UID 의 작업 세션은 원칙적으로 허브의 DB·credential 파일에 접근할 수 있으므로 **격리를 주장하지 않는다**. 대신 노출을 줄인다: 서버·수집 credential 과 human 토큰을 작업 세션의 env·argv·프롬프트에 넣지 않는다. 진짜 격리가 필요해지면 기존 isolation 계약(`README` 격리 절, `PALANTIR_AGENT_PROCESS_ISOLATION`)을 따른다.

#### 0.2.8 비서와 지시의 경계
- **관측 텍스트는 데이터다.** 다른 세션의 지시·응답·출력은 실행 권한의 근거가 되지 않는다. 살균은 credential 을 지울 뿐 지시의 신뢰성을 보장하지 않는다.
- **비서는 보내지 않는다.** 비서가 가진 것은 조회와 초안 작성뿐이다. 전송은 서버가 사람의 승인 뒤에 §0.2.6 계약으로 한다.
- **초안은 사람의 명시적 요청에서만 시작한다.** 비서가 관측한 내용을 보고 스스로 지시를 만들어 올리지 않는다. 승인 화면에는 사람의 원 요청, 대상·incarnation, 본문 전문, "비서가 작성한 초안"임을 함께 보인다.
- **사람이 소유 세션 채팅에 직접 친 지시는 비서를 거치지 않는다**(SH1 의 기본 경로). 비서 경유 초안은 SH5 에서 연다.
- §0.1 의 "다른 세션의 최근 출력은 사용자가 요청했을 때만 읽는다"는 유지한다. 소유 세션의 대화는 그 세션 자체의 화면이므로 이 제한의 대상이 아니다.

#### 0.2.9 인증·비용
- 소유 세션은 그 머신에서 사용자가 로그인한 CLI 인증을 쓴다. **구독 인증으로 프로그램이 세션을 구동하는 것이 벤더 약관·과금상 지원되는지, 과금 경로가 무엇인지를 SH1 착수 전에 확인**한다. 확인되지 않으면 SH1 범위를 정하기 전에 사용자와 판정한다.
- 비서와 작업 세션의 비용·사용량을 따로 보인다(provider 가 주는 범위에서).
- **인증 만료·한도 소진·계정 폐기**: 장애 사실과 턴 결과를 분리한다. 장애는 장애로 알리고, 진행 중 턴은 **실패 증거가 있을 때만 실패**로 표시하며 확인할 수 없으면 불명으로 둔다(§0.2.2·§0.2.6). 자동 재시도·재전송하지 않는다. 아직 보내지 않은 승인 대기 요청은 만료 처리한다.
- Codex 호스트: 실행 중 도구 승인은 현재 실험적 app-server 에만 문서화돼 있다. 따라서 **안정 경로로 승인을 줄 수 없는 동안 Codex 호스트는 "실행 중 승인 없음" 모드로 따로 수락**한다. 벤더 샌드박스 안에서 돌리고 `tool_approval` 미지원으로 표시한다. **승인 미지원을 승인 우회(`--dangerously-bypass-approvals-and-sandbox`)로 메우지 않는다.** app-server 승인은 버전을 고정한 opt-in 실험으로만 둔다.

#### 0.2.10 새 순서 (단계 이름 SH0~SH5 — 기존 I·C·S 트랙과 구분)
각 단계는 **필수 증거**를 내야 끝난다. 미달이면 보완 후 재평가할지, 중단할지를 사용자와 정한다(§7 의 원칙 그대로).

| 단계 | 내용 | 필수 증거 |
|---|---|---|
| **SH0** | 문서 개정(이 절 + README·CLAUDE.md 정체성) + C1 **기능 확대 동결**(측정·오귀속·보안 결함 수정은 계속) + Orca adapter 기본 끔 | **U7** — adapter 를 끈 것만으로는 부족하다. **Orca CLI·설정·Orca 가 만든 산출물을 쓸 수 없는 조건**(예: Orca 가 없는 머신)에서 C1 핵심 경로가 성립한다는 증거. + U1~U3 측정 보고. U1 분모는 측정 시점에 사용자가 직접 적은 열린 세션 목록으로 대조한다(registry·hook 은 미관측 세션을 못 찾는다). U1~U3 는 **C1 수락 판정**이며, 미달이어도 SH1 진입을 막지 않는다 — SH1 은 C1 과 독립인 습관 대체 검증이고, 미달 원인은 C1 보완 큐로 간다 |
| **SH1** | 사람용 세션 호스트, Claude 1개·머신 1대. 채팅에서 시작 → 직접 지시 → 도구 승인·거부 → 인터럽트 → 서버 재시작(재연결 또는 명시적 중단) → 터미널 resume 으로 넘기기. 별도 구현 brief | 선행: §0.2.6·§0.2.7·§0.2.9 확인. 증거 두 가지 — ① **사용자가 실제 작업에 써 보고 화면·흐름 lock-in**(사용성 1급, codex 위임 불가) ② **전달·복구 정확성**: 오입력 0, 중복 전송 0, 불명은 불명으로 표시(**U8 데스크톱 부분**). ①이 ②를 대신하지 않는다 |
| **SH2** | 수집 전용 인증 + 로컬 spool 수집기 + 살균·삭제 전파 + hooks 설치·제거 설계 | 설계검토 GO |
| **SH3** | hooks 를 머신 1대·Claude·Codex 둘에서 검증 | Orca 공존, trust 갱신, 미발화·유실·중복·순서 역전 실측. U7 재확인(hooks 경로) |
| **SH4** | 원격 머신 1대 + **폰 실기기**에서 SH1 경로 | 도달성·credential 폐기·오프라인 복구, **U8 폰 부분** |
| **SH5** | Codex 세션 호스트(§0.2.9 모드) + 통합 입구: 비서 초안(§0.2.8) → 서버 검증 → 사람 승인 → 소유 세션에 전달(§0.2.6) | 비서 경유 지시의 오대상 0, 승인 화면 고정 확인 |

순서 근거: 채팅 중심 결정으로 세션 호스트가 본류가 됐다. 이 경로가 사용자 습관을 실제로 대체하는지를 hooks 인프라보다 먼저 확인해야, 관측 인프라는 성공했는데 제어 제품이 실패하는 경우를 피한다. 대신 전달 안전·수명·인증 계약은 SH1 **앞**에 둔다.

## 1. 실측 (2026-10-06~08, 읽기 전용)

### 1.1 사용 규모와 토폴로지 (2026-10-08 사용자 확인 + 실측)

- **Palantir 운영 컨트롤 플레인은 codev1**, **주 작업 서버는 codev2** 다. 사용자 Mac 도 작업 머신으로 추가될 수 있다. 이전 기록의 "운영 = Raspberry Pi"는 더 이상 현행이 아니다.
- Orca 세션은 **처음부터 여러 머신에 흩어져 있다**. Mac(local)에 live terminal 28개, codev2(`--environment codev2`)에 worktree 15개와 훅이 추적하는 agent 11개가 있다. 이 밖에 Orca 가 아는 runtime 3개와 ssh host 2개가 `hostScope.omittedHostIds` 에 잡힌다.
- 따라서 **"여러 머신"은 나중에 확장할 축이 아니라 첫 슬라이스의 전제**다. 한 머신만 보는 보드로는 사용자의 실제 고통을 평가할 수 없다.

### 1.2 Orca 가 이미 주는 것

| 표면 | 내용 | 한계 |
|---|---|---|
| `worktree ps --json` | agent 별 `state`, `prompt`, `lastAssistantMessage`, `toolName`, `stateStartedAt` | `prompt` 는 **가장 최근 지시 하나**뿐이다. 이력이 아니다 |
| `terminal list/show/read` | 자동 생성 탭 제목, 미리보기, bounded 출력, 증분 cursor | 탭 제목이 첫 주제에 묶이기 쉬워 긴 세션의 주제 변화를 반영하지 못한다 |
| `orca search` | 에이전트 세션 전문검색 | **호스트 단위다.** CLI 원문: *"There is no all-computers search."* 이 Mac 에서는 인덱스가 `enabled:false` 상태였다 |
| 원격 | `environment add --pairing-code`, SSH relay, `orca serve` | — |
| 모바일 | 상태 확인, 완료 푸시, 짧은 응답 | 읽기 위주다. 데스크톱이 기준이다 |
| 코디네이터 | `orchestration coordinator-start` 는 **퇴역했다(no-op)** | Orca 는 "관리 에이전트"를 제품 기능으로 두지 않는다 |

### 1.3 연결 단서 — 확인된 것과 아닌 것

| 주장 | 상태 |
|---|---|
| Orca 는 터미널 프로세스 환경에 `ORCA_TERMINAL_HANDLE`, `ORCA_WORKTREE_ID`, `ORCA_TAB_ID`, `ORCA_PANE_KEY` 를 넣는다 | **확인**(이 세션의 프로세스 환경) |
| Orca 자체 훅은 이 값들과 함께 `launchToken`(실행 incarnation 구분자)을 읽는다 | **확인**(`~/.orca/agent-hooks/codex-hook.sh`) |
| 모든 실행 경로와 모든 훅이 이 환경을 물려받는다 | **미확인** — 재실행, resume, 중첩 에이전트 상황에서는 같은 handle 아래에 세션이 여러 개일 수 있다 |
| Claude Code 훅 설정에 SessionStart, UserPromptSubmit, Stop, StopFailure, PostCompact, SessionEnd 등이 설치돼 있다 | **설치만 확인**(`~/.claude/settings.json`). 실제로 발화하는지, payload 에 어떤 필드가 오는지는 미확인 |
| Codex 훅 설정에 SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, SubagentStart/Stop, Stop 이 설치돼 있다 | **설치만 확인**. **PostCompact 와 SessionEnd 는 없다** |
| transcript 가 지시 이력을 담는다 | **부분 확인**. Claude 는 `~/.claude/projects/*/*.jsonl` 약 160여 개, Codex 는 `~/.codex/sessions/**/rollout-*.jsonl` 약 4100여 개다(Palantir 워커 실행분 포함). Claude `user` 레코드의 대부분은 `tool_result` 이므로 **user 레코드 ≠ 사람이 제출한 지시**다. Codex 에는 `compacted`, `replacement_history` 같은 재구성 표현이 섞여 있다. 따라서 이 파일들은 "지원하는 버전에서, 보존된 파일 범위 안에서 복구 가능한 이력"일 뿐이다 |

**결론**: "터미널 = 세션 = transcript" 라는 등식은 성립하지 않는다. 둘 사이의 연결은 **시간 범위를 가진 관측 증거**로 다룬다(§3.1).

### 1.4 Palantir 가 이미 가진 것

| 축 | 자산 | 상태 |
|---|---|---|
| 잘하기 | goal 계약, Gate 1 acceptance, judge, Operator auto-review, B-lite 재시도, 메모리 주입 | goal 은 기본으로 꺼져 있다([goal-delegation-brief §6](./goal-delegation-brief.md)). **Palantir 가 spawn 한 실행에만 적용**된다 |
| 여러 머신 | nodes(local/remoteSsh), 원격 워커·Operator(실 Pi 실증), 원격 materialize, 노드 사용량 | 머신을 붙이는 절차가 무겁다(`runbook-fleet-deploy.md`). 운영 컨트롤 플레인(codev1)과 작업 머신(codev2·Mac)이 서로 다르다. 원격 대화형 입력은 스텁이다 |
| 찾기 | tasks/runs, 메모리 FTS5 | `unicode61` 토크나이저와 exact/prefix 매칭이라 **한국어 중간 부분어와 띄어쓰기 변형을 보장하지 못한다**(migration 025, `memoryService.buildMatchQuery`). 사용자가 Orca 에서 직접 내린 지시는 전혀 모른다 |
| 인증 | cookie(human) / bearer(human·PM 토큰) / worker·manager capability | PM 토큰과 human 토큰이 둘 다 **일반 bearer 로 통과한다**(`middleware/auth.js`). **수집 전용 권한이 없다** |
| 사용성 | 모바일 레이아웃 | visual baseline(빈 DB) 기준으로 문제가 보인다: 아이콘만 있는 하단 탭 6개, 매니저 화면 우측 잘림, 영문 원시 오류 노출, 숫자만 보여 주는 대시보드 |

## 2. 외부 근거 (deep-research, 3표 적대검증)

- **업계 동향**: "세션 페이지를 오가는 대신 지시·감독·검토를 한 화면에" 로 수렴하는 중이다(GitHub mission control, Codex app, Cursor Agents Window, Claude Code agent teams). 다만 업체 자료이므로 **방향을 보여 줄 뿐, 효과를 입증하지는 않는다.**
- **사람의 감독 방식**: 숙련 개발자는 실시간 모니터링을 거의 하지 않는다. 사후에 요약과 테스트 결과를 훑어보고, 간접 신호로 이상을 감지한다(arXiv 2606.05391, n=17, 비심사 preprint).
- **escalation**: 무차별 escalation 은 역효과를 낸다(arXiv 2606.08919, 시뮬레이션이므로 방향만 참고).
- **실패 원인**: 멀티에이전트 실패의 상당 부분은 조율·검증 설계에서 나온다. 검증 실패가 23.5% 를 차지한다(MAST).
- **기존 도구**: 범용 세션 전문검색 도구가 이미 있다(harness-recall). 다만 키워드로 회수만 할 뿐, 지시와 세션의 대응 관계는 주지 않는다.

### 2.1 독립 동작 근거 (2026-10-20 deep-research, 3표 검증 통과분만)
- **Claude Code hooks** ([공식 문서](https://code.claude.com/docs/en/hooks)): SessionStart·UserPromptSubmit(`prompt`)·Stop(`last_assistant_message`)·Notification(`notification_type` = permission_prompt / idle_prompt …)·SessionEnd, 공통 `session_id`·`transcript_path`·`cwd`. http hook 은 JSON 을 URL 로 POST(SessionStart 는 command 만). 허브 응답 실패는 non-blocking(이벤트 유실). "transcript 는 비동기 기록이라 늦을 수 있다 — `last_assistant_message` 를 쓰라". 전반적 안정성 보장 문구는 없고 일부 필드는 버전 조건이 있다.
- **Codex hooks** ([공식 문서](https://developers.openai.com/codex/hooks)): 현재 문서상 기본 활성, 12종(UserPromptSubmit·Stop·PermissionRequest·Interrupt·SessionStart·SessionEnd …), Notification 없음, 비관리 hook 은 해시 trust 검토. "the transcript format isn't a stable interface". 2026 상반기 2차 자료는 experimental/기본 off 로 적고 있어 설치 버전 확인이 필요하다. exec·app-server 맥락의 발화는 미문서.
- **codex app-server** ([공식 문서](https://developers.openai.com/codex/app-server)): thread/start·resume, turn/start·interrupt, 승인 요청 메서드가 있으나 "experimental and aren't supported for production workloads". 자기가 띄우거나 resume 한 thread 만 다룬다.
- **ACP** ([개요](https://agentclientprotocol.com/protocol/overview.md)): Apache-2.0, v1. session/new·prompt·update·cancel·request_permission. 에이전트는 클라이언트의 subprocess(stdio), 원격은 작업 중. Claude·Codex 는 어댑터 경유(codex-acp 는 app-server 위 번역, 태그 릴리스 없음).
- **OSS 관례**: 관측은 hook 우선 + 화면 판독 폴백(agent-deck: "Without the hook, turn-level running/waiting status cannot converge reliably"), 제어는 전부 **자기가 띄운 세션**만(Happy 는 `happy` 래퍼로 시작한 세션만 폰에서 이어받음, MIT). claudecodeui 는 SDK + node-pty + xterm.js, AGPL-3.0 + 추가조건.
- **결론**: 이미 떠 있는 남의 대화형 세션에 입력을 넣는 공식 경로는 어느 벤더에도 없다. → §0.2.4.
- **미검증**(검증 통과 0): tmux·PTY 입력 제출 신뢰성, 업계 감독 UX 동향, 다른 세션 텍스트를 읽는 비서의 prompt injection 연구. 이 부분의 §0.2 판단은 설계 판단이다.

## 3. 문제 재정의와 데이터 원칙

| 사용자 질문 | 필요한 것 |
|---|---|
| "이 세션 지금 뭐 하고 있지?" | 세션의 **최근 지시**, 마지막으로 관측한 상태, 관측 시각 |
| "이 세션 원래 뭐 하던 거였지?" | 세션의 **첫 지시**와 **지시 타임라인** |
| "아까 X 시킨 거 어디서 하고 있지?" | 지시 원문 검색 → 세션 역참조 |

세 질문 모두 **사람이 제출한 지시를 시간순으로 보여 주면** 답할 수 있다. 자동 목적 요약은 그다음 문제다.

### 3.1 데이터 원칙 (방향 단계에서 고정하는 경계)

1. **관측과 과업을 분리한다.** 1차 레코드는 "사람이 제출한 지시를 관측한 것"이다. 이를 논리적 과업으로 묶는 의미 병합은 I0~I1 에서 하지 않는다.
2. **연결은 다대다이고, 증거가 있을 때만 맺는다.** 증거가 없는 연결은 **불명**으로 표시한다.
3. **신원 축을 섞지 않는다.** 머신 신원, provider, 에이전트 `session_id`, 실행 incarnation, Orca 참조는 서로 다른 필드다. 실행 소유자(Palantir/Orca/수동)와 상호작용 방식(배치/대화형)도 별도의 축이다.
4. **외부 참조는 신원이 아니다.** terminal handle 과 transcript 경로는 관측한 시점의 위치 참조일 뿐이다.
5. **공통 계약은 관측으로 제한한다.** 원문(살균본), 출처, 발생 시각과 수신 시각, 원본 위치 참조, 세션 내 순서, coverage 까지만 다룬다. 제어 능력은 실행원별로 검증된 것만 노출한다.
6. **상태를 두 가지로 나눈다.** "마지막으로 관측한 이벤트"와 "생존·연결 상태"는 다른 사실이다. freshness 와 unknown 은 반드시 노출한다. 검증된 liveness 경로가 없으면 "현재", "입력 대기", "실패"를 추론해 표시하지 않는다.
7. **완료 권위를 섞지 않는다.** Orca 훅의 `done`, Palantir run 의 terminal 상태, goal verdict 는 서로 다른 사실이다.
8. **coverage 는 범위로 표현한다.** 수집 방식(live/backfill)과 별개로 시작, 끝, 공백, 마지막 대조 시각을 기록한다.
9. **유실과 순서 왜곡은 숨기지 않고 드러낸다.** 수집은 에이전트 실행을 막지 않는다. 수집하지 못한 구간은 coverage 공백으로 표시한다. 늦게 도착한 관측이 최신 상태를 과거로 되돌리지 않는다.
10. **사용자의 제외·삭제 의사는 재수집 후에도 유지된다.** 원본 transcript 를 지우지 않아도, 사용자가 제외하거나 삭제한 지시는 캐시를 재생성하거나 백필을 다시 해도 돌아오지 않는다. 보존 기간은 지시의 **발생 시각**을 기준으로 잰다(재수집 시점이 아니다).

### 3.2 세션 lineage 재판정 (OP §5-3)

OP §5-3 이 lineage 를 기각한 근거는 **투자 우선순위**였다("실사용 자동화와 action plane 이 먼저"). 이 brief 는 파악을 1순위로 바꾸므로 그 근거가 바뀐다. 그렇다고 lineage 를 바로 허용하지는 않는다.

- I0 에서 resume/fork 때문에 생기는 **중복·오귀속 사례가 실제로 몇 건인지, 영향이 얼마인지** 먼저 측정한다.
- 연결은 **명시적인 출처 증거**가 있을 때만 맺는다. 증거가 없으면 불명으로 남기며, 불명은 수락 가능한 상태다.
- 부모 연결은 측정 결과가 필요하다고 보여 주고, provider 지원 범위가 확인될 때 별도 구현 brief 에서 결정한다. **선행 필수 기능으로 고정하지 않는다.**
- lineage UI, DAG, 계보 탐색은 하지 않는다.

## 6. 성공 기준

**평가 방식은 1인 dogfood 다.** 표본을 작게 잡고 짧게 반복한다. 정확성은 측정 후 원본과 대조해 확인한다. 아래 임계값은 v1 이며, I0 에서 기준선을 잰 뒤 조정할 수 있다.

**공통 규칙**

- 결과는 **정답 / 오답(오귀속 포함) / 불명 / 자료 부족** 네 가지로 따로 집계한다. 불명과 자료 부족은 오답으로 세지 않지만, 비율을 함께 보고한다.
- 만족도("알겠다")와 정확도는 **별개 지표**다.
- 기존 방식(Orca 탭 순회)과 비교할 때는 **서로 다른 표본**을 쓰거나 **순서를 교대**한다. 먼저 한 방식이 다음 방식을 돕는 학습 효과를 피하기 위해서다.
- **최소 표본**: U1 = live 세션 10개, U2 = 세션 5개, U3 = 검색어 5개. 이보다 적으면 있는 만큼 측정하고 기록하되 **통과 판정하지 않는다**.
- **분모는 전체 표본**이다(불명·자료 부족 포함). 정답률 = 정답 ÷ 전체.
- 측정하는 동안에는 데이터 범위와 관측 기준 시각을 고정한다.

| # | 과업 | 측정 | 통과 기준 (v1) |
|---|---|---|---|
| **U1** | 열린 세션 각각이 무엇을 하는지 파악 | 측정 시점의 live 세션 전체를 대상으로 한다. 보드만 보고 세션마다 "하는 일"을 한 줄로 적는다. 다 적은 뒤 원본과 대조한다 | 정답 ≥ 85%, 오귀속 0, 소요 시간이 기존 방식의 절반 이하 |

## 7. 단계

각 단계는 **독립적으로 가치가 있어야 한다.** 다음 단계로 넘어갈지는 앞 단계의 측정 결과로 정한다. 뒤 단계를 예정된 결말로 승인하지 않는다.

### I0. 여러 머신 세션 보드 — 첫 슬라이스

공통 구성요소는 **읽기 모듈**이다.

- 작업 머신에서 실행된다. 사용자가 opt-in 한 **고정 경로 두 곳**(Claude·Codex transcript 디렉터리)만 읽고, 그 머신 안에서 살균한 관측만 내보낸다.
- 컨트롤 플레인은 작업 머신의 홈 디렉터리에 접근하지 않는다.
- 살균은 읽은 다음에 하는 처리라서 접근 경계를 대신하지 못한다. 경로 제한과 opt-in 이 1차 방어다.

모든 하위 단계에 공통으로 적용하는 계약은 다음과 같다.

- **parser**: 사람이 제출한 지시를 tool_result, 시스템 주입, compact 요약, 복제 이력과 구분한다. 텍스트가 없는 지시(이미지 등)는 "첨부 있음"으로 표시하고 coverage 공백으로 둔다.
- **화면**: 세션 카드, 지시 타임라인, 지시 원문 검색, 머신 표시. 연결이 모호해도 버리지 않고 **불명**으로 표시한다.
- **검색**: 기존 FTS 는 출발점일 뿐이다. 한국어 부분어, 띄어쓰기 정규화, 코드 식별자는 각각 별도 요구로 보고, U3 결과를 보고 필요한 것만 추가한다.
- **비밀**: §9-R2 의 살균을 읽기 모듈에서 적용한다.

#### I0a. 스냅샷 평가 (한시 실험)

- 읽기 모듈을 **Mac 과 codev2 에서 한 번씩 실행**해 살균된 관측 스냅샷을 만든다. 같은 시점의 `orca worktree ps` / `terminal list` 스냅샷(로컬 + `--environment codev2`)도 함께 뜬다.
- 화면은 Palantir 보드로 본다. 어디서 띄울지는 사용자가 정한다(로컬 인스턴스 또는 codev1 의 비운영 인스턴스). **상주 수집 데몬, ingestion 인증, 운영 DB 쓰기는 모두 없다.**
- 스냅샷이 고정돼 있으므로 §6 의 "측정 중 데이터 범위 고정" 규칙을 자연히 만족한다.
- **재사용 범위**: 읽기 모듈, parser, 살균, 화면, 검색은 I0b 이후에 그대로 쓴다. 버리는 것은 스냅샷을 수동으로 옮기는 경로뿐이다.
- **반출 경계 (작업 머신 밖으로 나가는 모든 스냅샷)**:
  - transcript 관측뿐 아니라 **Orca 스냅샷에도 같은 경계를 적용**한다.
  - Orca 자료는 신원·시각·상태·repo/경로·agent 종류 같은 **허용 필드만** 내보낸다. `prompt`, `lastAssistantMessage`, 미리보기, 탭 제목 같은 텍스트 필드는 반출 전에 제거하거나 살균한다.
  - 사용자 전용 목적지로만 옮기고, 인증되고 암호화된 경로를 쓴다.
  - 원본, 중간본, 가져온 사본은 repo 나 공유 위치에 두지 않는다. 평가가 끝나면 **세 곳 모두** 삭제한다.
  - 구체적인 도구는 구현 brief 에서 정한다.
- **종료와 수락은 별개다.**
  - 측정이 끝나면 실험은 종료된다.
  - 종료 보고에는 다음을 담는다: U0(I0a 에서는 준비 시간과 검색 응답 시간만, 반영 지연은 I0b 에서 측정), 표본 충족 여부, 기준별 결과, §3.2 의 중복·오귀속 실측.
  - **모든 기준을 통과해야** 화면 lock-in 과 I0b 진행을 판정한다.
  - 미달하거나 자료가 부족하면 중단할지, 수정한 뒤 재평가할지를 사용자와 정한다.
- **저장**: 화면이 lock-in 되기 전까지는 지시 데이터의 영속 스키마를 확정하지 않는다. 사용자의 제외·삭제 의사(§3.1-10)만 예외로 지속 저장한다.

#### I0b. 실시간 push 수집 → codev1

- I0a 화면이 lock-in 되면 읽기 모듈을 작업 머신의 **상주 수집기**로 바꿔 codev1 에 push 한다.
- 이 단계부터는 I2 의 수집 권한 보장이 **필수 선행 조건**이다. 머신별 수집 전용 capability, 서버가 derive 하는 머신 신원, human/PM 토큰 배포 금지를 모두 갖춘 뒤에 진행한다.
- 대상 머신은 codev2 와 Mac 이다. 이 단계에서는 transcript 를 증분으로 읽어 수집한다. 훅을 이용한 실시간화는 I1 에서 한다.
- **측정**: U0(반영 지연 포함)과 U1~U3 재측정.
  - U1 의 분모(측정 시점의 live 세션)는 **일회성 Orca 스냅샷**으로 확인한다. 이 스냅샷에도 I0a 의 반출 경계를 적용한다. transcript 만으로 liveness 를 추론하지 않는다(§3.1-6).
  - Orca 출력의 버전이 맞지 않거나 원격 조회에 실패하면 **자료 부족**으로 처리하고 통과시키지 않는다.
- **다음 단계로 가는 조건**:
  - 반영 지연이 원인이면 I1.
  - 머신 등록이 병목이면 I2.
  - U2 실패 원인이 *요약 필요*로 좁혀지면 목적 요약을 검토한다. 단, 귀속·coverage 문제를 먼저 배제해야 한다.

### I1. 실시간 수집 (훅)

- 사용자가 opt-in 하면 로컬 Claude Code / Codex 에 Palantir 수집 훅을 설치한다. Orca 훅과 **함께 동작**해야 하며, 설치와 제거 모두 할 수 있어야 한다. 설치 후 Orca 훅이 계속 동작하는지 검증한다.
- CLI·버전별로 이벤트와 필드의 **지원 범위를 실측**한다. "설치됨"과 "발화함"은 따로 확인한다. Codex 처럼 compact 이벤트가 없는 경우의 관측 경로도 정한다.
- resume, fork, compact, clear 상황에서 provider 별로 `session_id` 가 어떻게 바뀌는지 실측한다(§9-Q2).
- §3.1-9 의 보장(실행 비차단, 유실·순서 왜곡 가시화, 재전송 멱등, live 수집과 backfill 의 대응)을 지킨다. **구현 수단(spool, offset 등)은 구현 brief 에서 정한다.** 다만 내용 해시만으로 dedup 하는 것은 허용하지 않는다. 같은 문장을 두 번 제출하는 일도 실제로 있기 때문이다.
- 로컬 수집이라도 I2 의 최소 권한 모델을 그대로 쓴다. human/PM 토큰을 훅에 넣지 않는다.

### I2. 머신 추가와 등록 간소화

- 아래 수집 권한 보장은 **I0b 에서 이미 필요**하며, 이 단계는 그것을 모든 추가 머신으로 넓힌다.
  - 수집기는 **최소 권한**을 가진다. 수집만 할 수 있고, 머신별로 개별 폐기·회전이 가능하며, 크기와 빈도에 제한이 있다.
  - **머신 신원과 actor 는 서버가 인증 정보에서 derive** 한다.
  - **human 토큰과 PM 토큰은 절대 배포하지 않는다.** `auth.js` 에서 두 토큰 모두 일반 bearer 로 통과하기 때문이다.
- 수집된 지시는 **자동 수집자의 주장**이다. human-cookie 승인과 같은 효력을 갖지 않는다(R4 remember 의 actor split 을 유지한다).
- 실행용 fleet 노드와 **관측 전용 머신**을 구분한다. 관측 전용 머신에는 ssh 키나 CLI 사전 로그인이 필요 없어야 한다.
- 원격 transcript 백필을 위해 노드 executor 의 `exposed_roots` 를 넓히지 않는다. 대신 **수집기가 push** 한다(I0 읽기 모듈을 재사용).
- **수락**: U6. 세 번째 이후의 머신(Orca 가 아는 추가 runtime·ssh host 등)을 명령 한 줄 수준으로 붙일 수 있어야 한다.

### I3. attention + 관리 에이전트 조회

- 기존 `run:needs_input`, 질문 mailbox(격차①, #549~#553 완결), 실패, review 결과와 I1 의 관측을 합쳐 **걸러진 attention 뷰**를 만든다. "입력 대기"는 검증된 liveness 신호가 있는 실행원에만 표시한다.
- 관리 에이전트(Top)가 원장을 조회해 원문 근거와 함께 답한다. **모르는 부분을 추측으로 채우지 않는다.**
- OP 큐 #14 에 남은 항목(inbound inbox, T5 review ledger, T2 progress)은 이 단계에서 실제 소비자가 생길 때 필요한 범위만 연다.
- **수락**: U4, U5.

### I4. 지시 제출 경로 — 잘하기 연결

- Palantir(웹, 모바일, 관리 에이전트)에서 지시를 내린다. 관리 에이전트가 실행 위치를 고른다: Palantir 워커(검증 장치가 붙음) 또는 기존 세션.
- **보장 범위**: Palantir 경로로 들어온 지시는 **durable 접수**까지 보장된다. 접수는 실행이나 전달이 성공했다는 뜻이 아니다.
- goal 계약을 지시의 기본값으로 쓰려면 활성화 절차를 단순화해야 한다. 이때 [goal-delegation-brief §6](./goal-delegation-brief.md)의 보안 경계는 유지한다.
- 기존 Orca 세션으로 지시를 **전달**하는 것은 관측보다 강한 제어다. 그래서 별도 구현 brief 를 요구하고, 검증된 경로 하나에서만 연다.
- 지시 카드에 **검증됨 / 미검증 / 자기보고만** 배지를 단다.

### I5. 대화형 세션 흡수 — 트리거 대기

- 웹 터미널은 가장 비싸면서 모바일에서의 효용은 가장 작다.
- **트리거**: I0~I4 를 쓴 뒤에도 Orca 를 떠나지 못하는 이유가 대화형 터미널 하나로 좁혀졌을 때. 그때까지 Orca 는 대화형 실행기이자 이식 기간의 동작 기준으로 남는다(OP §6-5).

5. **사용자에게 정리 노동 요구**.
6. **lineage UI/DAG**(§3.2).
